# 《你的1000块钱，把我的一毛五吃掉了》
## —— FP16 精度丢失的底层原理与应对策略

---

> **提示**：如果你曾在模型训练里见过 loss 诡异地"卡住"，或梯度莫名衰减，别急着怀疑玄学。今天我们要聊的，可能正是那个在底层默默"吃数据"的家伙。

---

## 引子：一道看似无聊的"送命题"

在普通算术里：

$$1000.0 + 0.015 = 1000.015$$

没有悬念。

但在 FP16（半精度浮点数）的世界里，这个小数会被吃掉：

```python
import numpy as np

a = np.float16(1000.0)
b = np.float16(0.015)

print(float(a + b))  # 输出：1000.0
```

`0.015` 确实参与了运算，只是贡献幅度过小，未能跨越最终舍入的阈值。

从最终输出看，**像是蒸发了**。

就像是被 1000 这头大象一脚踩进了地板里——脚印还在，但你想找的那枚硬币，已经嵌在缝隙中看不见了。

这就是数值计算里的 **absorption（精度吸收）**，俗称**大数吞没**。

---

## 一、浮点数的基本结构：16 位能装下多少世界？

面对十进制小数，计算机会直接采用浮点编码，将其拆解为符号、指数与尾数三部分。以 FP16 为例：

| 部分 | 职责 | FP16 分配位数 |
|------|------|-------------|
| 符号位 | 正负号 | 1 位 |
| 指数位 | 数量级（`×2` 的幂次） | 5 位 |
| 尾数位 | 有效数字 | 10 位 |

**总共 16 位（2 字节）。**  
作为对比，FP32 尾数有 23 位，FP64 有 52 位。

FP16 像个"极限收纳师"：用最少的位数装下尽可能大的动态范围。但代价是——**有效精度最紧巴**，稍微大一点的数加个小数，就容易"装不下"。

---

## 二、浮点数相加的三个固定步骤

浮点数相加属于标准流程作业，必须按顺序走完三步：

1. **指数对齐**：小指数向大指数看齐，尾数相应右移。
2. **尾数相加**：在对齐后的位宽内做加法。
3. **规格化与舍入**：整理回标准格式，并按规则截断或进位。

精度丢失，往往就卡在这套流程的"对齐"与"舍入"交界处。

---

## 三、现象还原：0.015 是如何"消失"的？

以 `a = 1000.0` 和 `b = 0.015` 为例。在 FP16 中：
- `a ≈ 1.1111010000 × 2^9`
- `b ≈ 1.1110101110 × 2^{-7}`（注：0.015 在二进制下为无限循环小数，此处为 FP16 舍入后的近似值，实际存储约 0.0149994）

两者指数相差 **16**。为了对齐，`b` 的尾数必须向右移动 16 位。

移位后，`b` 的有效数字已完全移出 FP16 的 10 位主尾数窗口（含隐含前导 1 共 11 位有效精度）。即使硬件内部用 Guard、Round、Sticky 位暂存被挤出去的低位，其权重也远不足以触发进位。

**对最终 FP16 舍入结果来说，它不足以改变格点。**

最终判决：

$$a + b = 1.1111010000 \times 2^9 + 0 = 1000.0$$

`b` 的贡献被完全吸收。

---

## 四、真正的根因：FP16 在 1000 附近的尺子太粗

表面看，问题发生在指数对齐：`0.015` 的尾数被右移了 16 位。

但更深一层的原因是：**FP16 的精度分布具有非均匀性。**

浮点数不是一把普通尺子。  
它越往大数走，刻度越稀疏。

在 1000 附近，FP16 的指数是 9，尾数位宽是 10，因此：

$$1\ \text{ULP} = 2^{9-10} = 0.5$$

也就是说，FP16 在这里能"看见"的数大概是：

$$999.5,\ 1000.0,\ 1000.5,\ 1001.0$$

而你要加的是：

$$0.015$$

它只有一个 ULP 的 3%，连半个 ULP 的舍入门槛都碰不到。

所以最终结果不会停留在：

$$1000.015$$

而是重新落回最近的 FP16 格点：

$$1000.0$$

**这才是"大数吃小数"的根因**：  
问题的关键不在于小数本身，而在于 FP16 在该量级下的精度刻度过于粗糙，根本捕捉不到这么细微的增量。

---

## 五、为什么 AI 训练对这个问题格外敏感？

现代大模型普遍采用混合精度训练：前向计算用 FP16 省显存、提吞吐，但在累加等敏感环节必须格外谨慎。

神经网络的核心运算（矩阵乘、梯度累积等）本质上是海量 `acc += x * w` 的叠加。若累加器本身为 FP16，**在最坏情况下，误差会近似线性积累**。

例如将 0.015 连续加 100 次到 1000 上：

```python
import numpy as np

acc_fp16 = np.float16(1000.0)
acc_fp32 = np.float32(1000.0)
for _ in range(100):
    acc_fp16 += np.float16(0.015)
    acc_fp32 += np.float32(np.float16(0.015))

print(f"FP16 累加器: {float(acc_fp16)}")      # 输出: 1000.0
print(f"FP32 累加器转回 FP16: {float(np.float16(acc_fp32))}")  # 输出: 1001.5
```

100 次累加，FP16 的结果纹丝不动。

在实际训练里，这意味着：
- **梯度累积**：大量小梯度被累加器吸收，反向传播信号逐渐衰减
- **Attention 打分求和**：分母截断，归一化权重分布悄悄漂移
- **LayerNorm 统计量**：均值与方差计算失真，训练动态变得不稳

最典型的表现是：明明喂进去一堆微小更新，累加器却像"吃撑了"一样毫无反应。

---

## 六、标准解法：高精度中间累加

规避这个问题的工程惯例很直接：**先升精度累加，完事再降回来**。

```python
# 危险操作（FP16 直接累加）
total = fp16(0.0)
for x in many_small_values:
    total += fp16(x)   # 精度被吸收，累加停滞

# 正确操作（FP32 中间累加）
total = fp32(0.0)
for x in many_small_values:
    total += fp32(x)   # 尾数足够，保留低位贡献
total = fp16(total)    # 最终结果转回目标精度
```

为什么有效？FP32 拥有 23 位尾数（含隐含位共 24 位有效精度）。在指数差 16 位的情况下，**右移后的小数有效位仍落在 FP32 的有效精度范围内，不会像在 FP16 中那样被挤出主精度窗口**。

这种设计早已成为现代 AI 芯片的底层规范。**NVIDIA Tensor Core 从 Volta 架构起就原生支持这类混合精度路径**：
```
FP16 输入 × FP16 权重 → FP32 累加器 → FP16 输出
```
乘法在 FP16 里跑，拿高吞吐；累加强制走 FP32，守精度底线。Ampere（TF32）、Hopper（FP8）等后续架构均延续了这一"精度隔离"思路。

**但请注意**：是否使用 FP32 累加，取决于具体指令、算子和框架配置。普通的 FP16 标量或向量加法可不会自动"开小灶"，别误以为"只要跑在 GPU 上就安全"。

---

## 七、设计取舍：为什么 FP16 只有 10 位尾数？

既然有坑，为什么还要广泛使用？典型的工程权衡而已。

尾数位宽直接决定数据体积与带宽压力。在大模型场景下，显存容量与内存带宽往往比纯算力更卡脖子。将 FP32 降至 FP16，显存占用直接减半，数据搬运效率与计算吞吐成倍提升。

设计者的账算得很清楚：常规前向与推理中，数值动态范围通常不会频繁触发精度吸收；而在确实存在风险的关键路径上，交给 FP32 累加器兜底即可。

**用可控的精度让步，换显存和吞吐的跨越式提升。**  
代价明确，收益可观。

---

## 总结：一把刻度不均匀的尺子

FP16 的 10 位尾数决定了它的精度分辨率。当操作数指数差接近或超过有效位宽时，小数在指数对齐过程中会被右移至精度窗口之外；若其贡献低于当前大数附近的半个 ULP，舍入机制便会将其静默丢弃。

**应对方法**：在累加、归一化等对精度敏感的操作中，使用 FP32 作为中间累加器，完成计算后再转回 FP16。**这会增加累加器寄存器资源、部分计算开销，并在某些实现中带来额外中间存储成本，但能显著提升数值稳定性**。

最后，留个直观的比喻帮助记忆：

> 把 FP16 想象成一本只有 10 格的账本。`1000` 已经写满了前 10 格，而 `0.015` 需要落在第 17 格。但账本只有 10 格，多出来的部分只能被直接抹掉。  
> 换成 FP32，账本有 24 格有效位置，第 17 格稳稳在记录范围内。

理解这一点，下次再调精度或看 loss 曲线时，你就能一眼看穿：到底是模型没学好，还是底层加法器在"偷懒"。
